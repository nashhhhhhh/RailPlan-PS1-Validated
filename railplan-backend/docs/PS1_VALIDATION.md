# Internal provisional PS1 submission validator

Version: `ps1-validator/1.1.0`. Policy: `ps1-policy/2-explicit-night-alignment`.
**Judge validation not run. Objectives are internal, not officially verified.**
This validates uploaded schedules; it does not optimise, generate schedules, approve track
access, use AI or translate PS1 activities into nightly maintenance requests. Input imports,
immutable instances and legacy features are preserved. Conflict severity is separate from
schedule objective.

## Running and UI

Install backend dependencies and run `uvicorn app.main:app --host 127.0.0.1 --port 8000`
from `railplan-backend`. Preview requires no PostgreSQL or authentication. In the PS1 UI,
load the organiser dataset or import eight CSVs, select A/B/C, upload the three submission
CSVs, and select **Preview Scenario**. Reference downloads remain labelled organiser
outputs, not schedules generated by RailPlan.

The panel shows feasibility, workload completeness, hard violations, separate objective
components, capacity hotspots, warnings and assumptions. Filter violations by rule/week;
select one to highlight its activities, week, locations and network stations. The supply
tab also highlights affected location rows. Download JSON retains the complete report.
Save the dataset before persisting a validation. Saved reports can be reopened via history.

## API

| Endpoint | Input / output | Access |
|---|---|---|
| POST `/api/ps1/validate` | `{scenario, instance_files, files}` → report | Stateless, no auth/DB |
| POST `/api/ps1/instances/{id}/validations` | `{scenario, files, idempotency_key?}` → `{id, created, report}` | Planner or administrator |
| GET `/api/ps1/instances/{id}/validations` | Paginated metadata | Same-operator authenticated user |
| GET `/api/ps1/validations/{id}` | Run with exact sources and snapshots | Same-operator authenticated user |
| GET `/api/ps1/validations/{id}/violations` | Paginated evidence; optional `rule_code` | Same-operator authenticated user |

`files` maps the three exact submission filenames to CSV strings; `instance_files` maps
the eight input filenames to CSV strings. User-supplied parsed datasets and policies are
not accepted. Persisted runs use the saved immutable instance. Demo identity still uses
`X-Demo-User-Id`; production authentication is outside this change. Pagination uses
`limit` (1–200) and `offset` (0–100000).

Validation reports return HTTP 200 even when infeasible: the operation succeeded, not the
schedule. CSV errors become structured violations. Invalid JSON/Pydantic fields or invalid
instance inputs return the established 422 envelope. Content/key collisions return 409;
other-operator resources return 404; excessive wire bodies return 413.

## Architecture, limits and determinism

- `contracts.py`: typed wire contracts, frozen versioned policy and limits.
- `submission.py`: strict CSV parsing and exact-source fingerprints.
- `network.py`: independent canonical platform/tunnel expansion.
- `rules.py`: pure hard rules, workload and capacity diagnostics.
- `scoring.py`: Decimal components and independent RESULTS derivation.
- `service.py`: stable orchestration; `persistence.py`: transactional storage only.

Headers must match exactly, including order. Missing values, unknown columns/IDs, invalid
dates/integers/ECLO, mixed scenarios and duplicate logical records are rejected. Logical
keys are access `(activity_id,access_seq)`, occupancy `(activity_id,week,location_id)` and
result `(contract_number)`. All duplicated accesses are excluded from workload credit.
Ambiguous/missing occupancy groups get separate synthetic slots, so deletion cannot hide
supply use. Uploaded content is never executed or interpreted as spreadsheet formulas.

Each instance/submission is bounded to 4 MB of CSV text. Submission files have at most
20,000 rows and 256 characters per cell, with no control characters. POST wire bodies are
bounded to 10 MB before JSON allocation, including chunked requests. At most 20,000 distinct
intersecting activity-pairs are evaluated; exceeding this computational budget rejects
the submission as invalid, records `physical_evaluation_complete:false` in evidence, and
leaves diagnostics partial. Accepted submissions never silently truncate violations.

All output lists are stably sorted. Dataset row order cannot alter a report. CSV row order
can change the source fingerprint, but not semantic diagnostics. SHA-256 hashes sorted-key
JSON containing exact CSV strings, retaining BOM and line-ending distinctions.

Every violation includes code, message, nullable week, sorted activity/contract/location
IDs, nullable possession group and structured evidence. Physical evidence includes the
relevant location group assignments, not only human-readable descriptions.

## Geometry and provisional assumptions

Cached spans and uploaded occupancy never determine physical truth. Stations are ordered
per line; sectors join by endpoints, not their global sequence number. Tunnel endpoints
include book-in/out platforms. Reverse endpoints are supported. Live expands by two
sectors each side, Consist by one, Others by none; expansion includes platforms and clips
at line ends. Only Live mirrors its entire expanded closure. Live touching H01/H02 or
H01_H02 through its expanded footprint closes those three locations on both bounds of
the other line. Cross-line expansion is not recursive. Non-live never merges capacities.
Buffers/mirrors are exclusion footprints, not occupancy rows or extra supply consumption.

**Night alignment remains ambiguous:** `access_night` is local to contract/type/week.
`co_share_group` is local to location/week and the sample changes labels along one access.
Neither identifies a shared railway calendar. This version uses:

1. Different groups at a common occupied location represent different nights there.
2. Legal sharing at every common occupied location exempts a pair from mutual closures.
   A matching label at unrelated locations grants no exemption.
3. CSV-only buffer/opposite/cross-line candidates produce deterministic
   `physical_night_alignment_unverifiable` warnings containing week, activity IDs,
   candidate collision type and locations. They are not proof of a conflict.
4. Python callers may pass `validate(dataset, files, scenario, physical_nights=...)`,
   where the mapping is `{(activity_id, week): positive_integer_night_id}`. These
   IDs are shared across the network within a week, not local allocation indices.
   Every scheduled activity/week must be present exactly once, with no extra keys.
   A location/week possession group must map to one physical night. Invalid or
   incomplete mappings fail closed with a schema violation and a null objective.
5. Rich validation indexes `(week, physical_night, location)` and checks same-night
   physical overlaps as hard violations. Distinct groups on the same occupied
   location and physical night collide; legal sharing retains its exemption.
   Local labels at unrelated locations never establish concurrency or exemption.

Reports expose `validation_context` and `physical_validation_complete`. In submission
context, `feasible:true` means the verifiable CSV constraints passed, not physical
safety clearance. Rich context means the explicit-night physical checks were run;
other geometry and scoring assumptions remain internal and provisional. Validation HTTP
inputs remain CSV-only; tuple-key mappings are a Python solver interface, not JSON inputs.
The separate [Scenario A optimiser](PS1_OPTIMISATION.md) now generates explicit physical
assignments and calls this rich interface before returning usable CSVs.
Rich submission fingerprints include sorted physical-night assignments, distinguishing
different alignments while remaining invariant to mapping insertion order.

Obtain the reference validator to settle
cross-location alignment, partial-span exemptions, buffer endpoints, buffer-triggered
interchange closure, mirrored platforms and whether closures consume supply. Update the
policy/validator versions rather than changing old run snapshots. Never claim parity.

Completion is Sunday of the last submitted access week, only after full workload delivery.
Extra accesses remain counted and can extend completion. Dependencies require a strictly
later week, because local indices cannot order different contracts' nights. These conventions
(last access versus earliest workload completion, same-week dependencies, horizon limits)
also need official comparison. Multiple contract types must have consistent planned dates
and contract priorities before deriving their single RESULTS row.

## Exact arithmetic and scores

Normal access yields Decimal `1.0`; ECLO yields `1.5`; sharing never reduces workload.
Over-delivery is reported separately. Contract completion is the latest completed activity;
raw contract overrun counts each contract once. Weighted overrun sums each activity's delay
against its contract/type planned date, with contract tier weights 100/10/1 and activity
multipliers 1.3/1.2/1.0. Contract-priority raw tier totals are separate from activity costs.
Explicit numeric formulas override contradictory qualitative prose in the supplied README.

| Scenario | Objective | Hard conditions |
|---|---|---|
| A | weighted overrun | No excess, no ECLO |
| B | 7 × excess + 5 × ECLO | No planned-date overrun; excess is unlimited but scored |
| C | weighted overrun + 7 × excess + 5 × ECLO | ≤1 excess/location/week; two-week ECLO span/line |

ECLO count is per activity access, not inferred global nights. Raw overrun, weighted
overrun, excess, ECLO and penalties are exposed independently. Decimal `ROUND_HALF_UP`
produces two-decimal score strings; workload uses one decimal. Any hard violation sets
`objective_score:null`. `diagnostic_objective` is not an eligible objective; incomplete
activities have null dates/delays and `metrics_complete:false`.

## Unmodified public sample

All 54 activities deliver all 192 standard workload units. All 14 RESULTS rows agree with
derived dates. There are no schema, workload, possession-mix, supply or result errors.
Raw contract overrun = 28 days; weighted activity overrun = `48.30`; excess = 0; ECLO = 0.

**The unmodified sample passes CSV-only validation**, with zero hard violations,
internal objective `48.30` and 70 alignment warnings. Physical-night validation remains
incomplete because the CSVs do not supply a global alignment. The organiser README calls
the sample feasible; this agreement does not establish judge parity. The actual
`trackaccess` reference validator is not supplied. Inputs and sample files are unchanged.

## Persistence and remaining verification

Migration 0006 follows 0005. Runs retain exact CSV text, both fingerprints, version,
scenario, policy, full report, creator, operator and timestamps. Violations also have
ordered indexed rows. A third immutable table stores every idempotency alias, including
new aliases for existing content. Composite parent/operator FKs and scoped queries enforce
ownership. Insert audits plus UPDATE/DELETE/TRUNCATE triggers protect all new tables.
The existing session transaction commits runs/evidence/keys/events together or rolls back.
Transaction advisory locks serialize keys then identical content. Identical
instance/submission/version reuses a run. Reusing an operator-scoped key for other content
returns HTTP 409, including across instances.

Run `python -m pytest -q`; `python -m scripts.export_contracts`; root
`npx tsc --noEmit --strict` and `npm run build`; `npm test` in `railplan-backend/frontend`.
Database tests require an explicitly configured safe `TEST_DATABASE_URL` pointing to an
empty disposable database named `railplan_test...`. Without it they skip. Do not use production.
Tests cover retention, deduplication, aliases, collisions, isolation, roles, FKs, audit,
immutability and rollback. PostgreSQL execution, browser interactions, concurrent load
testing and official-validator comparison remain outstanding. The validator itself adds
no approval, solver, AI or production authentication. Scenario A optimisation is separate.
