# RailPlan

RailPlan is a rail-maintenance planning prototype with a React/Vinext dashboard and a
FastAPI backend. The PS1 workspace imports the organiser's eight source CSVs, explains
their lineage, renders the Line Alpha/Line Beta topology, previews all three validation
policies, and runs the Scenario A CP-SAT optimiser. The organiser submission samples are
reference schedules; they are not presented as schedules generated by RailPlan.

The internal validator supports Scenarios A, B and C. This authoritative checkout contains
the Scenario A optimiser source. Scenario B and C optimiser source/release archives were not
present, so this release does not substitute new implementations for them.

## Run locally with one command

Requirements are Python 3.11+ and Node.js 22.13+ with Corepack. From the project root:

```powershell
python app.py
```

This creates the backend virtual environment when needed, installs pinned frontend
dependencies, and starts FastAPI plus the dashboard. Open `http://127.0.0.1:5173`.
Stateless dataset parsing, validation and `POST /api/ps1/optimise/scenario-a/preview`
work without a database or authentication.

Persisted mode also requires Docker and a shell-only password:

```powershell
$env:POSTGRES_PASSWORD="choose-a-local-password"
python app.py --persisted --seed
```

Persisted mode starts the existing PostGIS service, applies migrations through `0009`,
and enables immutable instances, validation history, optimiser runs and asynchronous jobs.
Environment files and secrets are excluded from source packages.

## Separate development commands

Backend:

```powershell
cd railplan-backend
python -m venv .venv
.venv\Scripts\python -m pip install -e ".[test]"
.venv\Scripts\python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Frontend, from the project root:

```powershell
corepack pnpm install --frozen-lockfile
corepack pnpm dev
```

API documentation is available at `http://127.0.0.1:8000/docs`.

## PS1 scheduling terms

- `physical_night` is a network-wide night slot within a calendar week. It is the value
  used to test simultaneous closure, buffer, interchange and opposite-bound conflicts.
- `access_night` is a local ordinal inside one contract/activity-type/week allocation.
  Equal local ordinals do not prove that two activities occur together.
- `co_share_group` is a possession label scoped to one location and week. Matching labels
  at different locations do not create a global possession or physical-night alignment.

The bundled data has no authoritative dated engineering-night calendar. The mapping from
slots 1..7 to actual nights remains a provisional policy assumption. Internal
publishability means the rich validator accepted a complete explicit-night candidate; it
does not mean judge acceptance or operational approval. `judge_validation` remains
`not_run`, and `score_verification` remains `internal_only`.

AI assistance through Ollama/Qwen is optional. It is not used by parsing, constraint
generation, feasibility, scoring, validation or the optimiser publication gate.

## Verification and deployment

```powershell
cd railplan-backend
.venv\Scripts\python -m pytest -q
cd ..
corepack pnpm exec tsc --noEmit
corepack pnpm test:ps1
corepack pnpm build
```

PostgreSQL tests require disposable databases whose names begin with `railplan_test`; see
[the persistence test guide](railplan-backend/docs/PS1_PERSISTENCE_TEST_GUIDE.md).
Browser checks are described in [the UI integration guide](docs/PS1_UI_INTEGRATION.md).
Production container setup and variables are in
[DEPLOYMENT.md](railplan-backend/docs/DEPLOYMENT.md). The exact release evidence and known
limits are in [RELEASE_VERIFICATION.md](RELEASE_VERIFICATION.md).

This prototype does not grant track access, electrical switching or worker deployment
authority. Production deployments must provide verified identity and the official railway
rules, calendars and validator.
